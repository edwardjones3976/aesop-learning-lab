Micro-unit engine (A3)

aesop_lab.micro.engine.MicroUnitEngine(pack, store, now, daily_limit=3) uses a validated MicroUnitPack, a SQLiteStore, and a callable clock returning an aware datetime. This is an engine/storage API; existing Python content, Preview, protocols and UI continue on their existing paths.

API

  • next_activity() returns a dictionary (kind="check" or kind="unit"), or None. Checks include the prompt and check ID, without the key. A new unit suggestion includes its ID; call start_unit to receive its lesson. A suggestion does not reserve or expose content. Unfinished units can resume.
  • choose_method(unit) returns a method ID. Existing assignments are stable. Before assignment, this is a deterministic proposal given the current history; feedback or assignments arriving before start_unit can change the proposal.
  • start_unit(unit) persists assignment and exposure and returns only the assigned variant in lesson, plus the method and unit IDs. Repeated calls on unfinished units preserve the method and original timestamps. Completed units are refused. New assignments count toward the daily cap; existing units can resume after that cap. The assignment transaction serializes competing connections, including warm-up and cap decisions.
  • complete_unit(unit) records completion once. The unit must have started.
  • answer_check(unit, answer, assisted=False, outside_study="unknown", previously_seen=False) scores using the existing normalize_answer (whitespace normalized) and then ignores case on both sides, so RIVER matches river; punctuation must still match. It compares against the candidate accepted strings. It returns the persisted first response, score and classification. Repeats cannot replace the first response, including an early, assisted or incorrect response. Completion is required; direct early or late submissions are retained for reporting.
  • outcomes_by_method() returns all methods mapped to (matched_key, 1.0) observations under outcomes, and unit IDs under excluded for early, late, assisted, contaminated, pending and missing. A completed unit with no response is pending while its day-14 window is open (elapsed time 14 days or less), and missing only after the window closes. Uncompleted units add no evidence. Contamination takes precedence over assistance, then timing in these mutually exclusive buckets.
  • ranking() returns ordered methods with method, posterior_mean, probability_best, effective_checks, alpha, beta; plus confidence, show_ranking, and exclusions. It delegates to #60's rank_methods unchanged.

Dictionary outputs and each ranking method carry provisional="provisional (draft keys)". Draft keys never block estimating or returning an ordering. show_ranking retains #60's evidence availability rule. Method IDs returned by choose_method are identifiers, not learner wording. Units can be passed as IDs or pack unit objects; the canonical pack object is used.

Schedule and eligibility

Unanswered checks are offered first, oldest completion first, once elapsed time since completion reaches seven full days. Overdue checks remain answerable and are classified late. Checks never consume the new-unit allowance. Then unfinished units resume, then the first unseen unit in seeded learner order is suggested if the daily allowance permits it. Assignment dates use calendar days in the timezone supplied by now; step C must consistently supply the learner's chosen timezone. The default cap is three new units per calendar day per pack.

The descriptive protocol's exact inclusive window applies: before seven elapsed days is early; exactly seven through exactly fourteen days is in-window; after fourteen days is late. Only received, first, unassisted, in-window responses feed assignment posteriors and ranking, once per exposure at weight one. No imputation for missing checks, practice scoring, or repeated-check evidence is added.

Storage and #60 mapping

Schema v17 introduced micro_exposures and micro_check_attempts. Both use (pack_id, unit_id) as primary key: one exposure and one decisive check per unit in a learner's local database. Exposure rows hold method and assignment, exposure and completion timestamps. Check rows hold check ID, first answer, correct/incorrect score status, timestamp, and assisted flag; a composite foreign key references the exposure. Every new storage write calls require_active_learner. export_all includes microExposures and microCheckAttempts; delete_all removes checks before exposures, retaining the existing secure deletion behavior. The additive v16 migration does not rewrite existing tables or learner history. The real compressed v16 fixture and its provenance are in tests/fixtures/micro-v16.md.

Assignment uses a SHA-256 seed from learner ID, pack ID and unit ID, with a local RNG and sorted method IDs. Warm-up picks among methods with the fewest assignments until each has two within its block, including pending checks. Thereafter a 20% uniform draw and 80% independent Beta Thompson draw use only received eligible outcomes. Priors are Beta(1,1), success/failure increments are one. This implements #60's policy and independent-unit rule without changing its estimator or confidence thresholds. A learner ID is created only behind consent. Ranking Monte Carlo is separately seeded from learner/pack and the string ranking.

A3 hardening

Schema v18 adds exposure TEXT columns policy_branch, assignment_seed, eligible_choices, policy_version, pack_version, and reexposed_at. Check rows gain outside_study (TEXT, default unknown, restricted to none/some/unknown) and previously_seen (INTEGER boolean, default 0). All columns are exported. Additive migration preserves every prior row; legacy provenance remains NULL because historical decisions cannot be reconstructed. Unlogged replays from before this fix cannot be identified retrospectively.

Before exposure, new engine assignments atomically store the branch (warm-up, uniform-20, thompson), decimal SHA-256 seed, JSON eligible method IDs, policy version thompson-80-20-warmup2-block-v1, and pack schema version plus SHA-256 of the parsed pack representation. The branch is stored instead of an exact assignment probability. Replaying adaptive decisions also requires the received history.

The pack format accepts an optional nonempty block string per unit, for example "block": "difficulty-1". Omitted blocks share one stratum. Warm-up counts assignments within the current block, including pending checks, until each method has two. Thereafter that block uses the 20% uniform exploration branch and 80% global Thompson branch. Uniform exploration samples all methods; exact equal counts are not guaranteed. Thompson uses eligible outcomes across all blocks. Blocks should identify topic/difficulty strata before enrollment.

Unit scheduling uses a learner/pack SHA-256 seed with the separate string unit-order to shuffle the pack. Order is stable across restart and varies across learners. Checks retain priority and the daily cap applies. Explicit start_unit calls may select by ID; callers should follow next_activity to retain random scheduling. Packs remain immutable.

start_unit raises ValueError: completed unit cannot be replayed after completion. Refusal does not expose content or contaminate the check. Unfinished restarts return the original assigned lesson and retain timestamps. Every engine lesson-return path marks exposure. Any lower-level exposure after completion persists the first reexposed_at; it permanently excludes that unit's check, even if already answered.

answer_check(unit, answer, assisted=False, outside_study="unknown", previously_seen=False) persists the structured declarations with the first answer. Outside study some, prior familiarity, or recorded re-exposure yields contaminated, reported in excluded and excluded from both allocation posteriors and ranking. Contamination takes precedence over assistance and timing. Unknown and none are not reports of outside study, matching descriptive_v2.py; they remain eligible when other requirements pass. Repeated submissions preserve the first response and declarations.

Validation and deliberate breaks

The balance test schedules 24 units (two blocks of 12) for 300 learners without received feedback. It requires more than 290 distinct orders, mean original pack position spread below 0.8 across methods, and per-block method count spread below 160 of 3,600 assignments. Adaptive allocation need not have equal counts when feedback differs. A separate test verifies two warm-up assignments per method in each block.

Existing expectations changed only for schema v18, shuffled next-unit order, unfinished instead of completed restart, and the added contaminated bucket. The consent migration test now expects v18. Existing Python content, Preview, protocols, estimator and UI are unchanged.

PYTHONPATH=src python scripts/micro_unit_engine_break_checks.py runs isolated in-memory mutations that must cause assertion failures, without import/runtime errors. New mutations remove replay refusal, ignore re-exposure, omit provenance, pool block warm-up, remove shuffle, and ignore outside study or familiarity. The original A2 mutations remain.

Final validation: Python unittest discovery passed 343 tests (including 18 engine tests); Node contract suites passed 51 tests. Across 300 learners, mean original pack positions were 11.5652, 11.5395 and 11.3959 in sorted method order (spread 0.1694, limit 0.8). Easy-block counts were 1201/1184/1215 and hard-block counts 1207/1198/1195 (spreads 31 and 12, limit 160). Both order-diversity and per-block warm-up assertions passed. Deliberate mutation checks detected 20/20 breaks through assertion failures, including v17 migration and optional block parsing. One intermediate full run encountered a Windows connection-abort error in an existing HTTP journey; the full suite was rerun. No push, PR or merge was performed.

Step C decisions

HTTP routes and payload contracts, UI integration, learner timezone selection, pack enrollment/switching, explicit assistance capture, and wording for pending, missed, late and close results remain for step C. The engine supplies exclusion IDs and model confidence; the UI must explain draft-key uncertainty and must not imply the leader's confidence certifies the entire ordering. Pack IDs must be stable and packs immutable during a run; versioning or replacing enrolled content needs a separate policy. No push, PR, approval or merge is part of A3.
