Consent gate: round 2, step 8

Local implementation on feat/consent-gate, based on f5b700e3481eefd0b86f5d22804e50d920e8c0cb. No push, PR, approval or merge. Claude integrates; Cursor reviews/merges under the existing gates.

Schema v16 adds learner_consent(slot, text_version, confirmed_at). Confirmation is idempotent and records consent-v1 before any enrollment. Export includes raw records as learnerConsent. Deletion removes consent atomically with learner data; the existing tombstone prevents re-enrollment until Start again. Restart only clears that tombstone, so new consent is then required.

Legacy choice: migration, rather than lazy recording. Existing identities receive legacy-pre-gate and the migration's UTC timestamp; this timestamp is not represented as an earlier affirmative consent. Existing runs continue. The gzip fixture was generated using the unchanged v15 base code, with a lesson opening, before editing storage. Its test compares every preexisting table row.

The consent screen replaces the workspace and navigation until confirmed, has one button (I agree — start learning), and no inputs. Its shipped text is:

Your answers, hint use, confidence, outside-study notes and timing are stored on this computer only. They are not sent to any outside service, including AI models.

Results are compared with draft answer keys. They stay provisional and are not a grade or a judgment of what you know.

One person's answers are not enough evidence to show which teaching method works better.

You can stop at any time, and you can ask for your data to be deleted.

The phrase about a judgment of what you know expresses the requested limit without putting the word mastery into consent markup.

Enforcement uses SQLiteStore.require_active_learner, preserving the prior learner_deleted priority and adding HTTP 409 consent_required. Preview and learning-service entry points enforce it, with an additional HTTP route guard. The v2 response retains error and also exposes code.

Gated v2 endpoints:

  • GET /api/v2/session, /api/v2/personal-comparison.
  • POST /api/v2/lesson, /api/v2/lesson-completions, /api/v2/first-answers, /api/v2/hints, /api/v2/attempts, /api/v2/self-reviews, /api/v2/revisions, /api/v2/overrides.
  • POST /api/v2/personal-comparison/{enroll,start,complete,open,hint,answer,reveal,override}.

GET overview and export stay read-only and available before consent. Overview includes consentRequired; export creates no identity. POST consent records only consent. Delete and restart remain available and create no learner rows.

The v1 API can write learner state, so the gate also covers GET /api/v1/session/next and POST /api/v1/attempts, /api/v1/self-reviews, /api/v1/answer-revisions, plus the underlying lesson-completion service. Export and deletion remain available. No v1 consent route was added; confirmation is through the preview or storage, with v1 changes limited to enforcement. No protocol modules, packs, or classifications changed. Runbook step 1 retains the owner's conversation, describes the app record and removes the workaround. Step 3 and 4 command blocks compare byte-for-byte equal to the base content.
